The most common production incident I see when teams first containerize Java is not a slow app or a crash in the code. It is a container that silently restarts every few hours with exit code 137. The JVM never logged an OutOfMemoryError. The kernel simply killed it. The cause is almost always the same: the heap was sized as if it were the only thing in the container.

The heap is not the whole JVM

The memory limit on a container applies to the whole process. For a JVM, that is a lot more than the heap:

  • Heap: your objects, controlled by -Xmx or MaxRAMPercentage.
  • Metaspace: class metadata, which grows with every library and framework you load.
  • Thread stacks: up to 1 MB per platform thread by default.
  • Code cache: compiled JIT code, often 50 to 240 MB.
  • Direct buffers: off-heap memory used by Netty, NIO, and many HTTP clients.
  • GC overhead: the collector's own data structures.

Set -Xmx1g in a container with a 1 GiB limit and the heap alone can fill the container. Everything else pushes it over, and the kernel's out-of-memory killer ends the process with SIGKILL, which is the 137 you see in docker ps -a or kubectl describe pod.

Let the JVM read the container limit

Modern JVMs are container aware: they read the memory limit from the cgroup instead of the host's total RAM. That means you can size the heap as a percentage of the container, and the same image works whether you give it 512 MiB or 4 GiB: 

FROM eclipse-temurin:27-jre
COPY app.jar /app/app.jar
ENV JAVA_TOOL_OPTIONS="-XX:MaxRAMPercentage=70 -XX:+ExitOnOutOfMemoryError"
ENTRYPOINT ["java", "-jar", "/app/app.jar"]

MaxRAMPercentage=70 gives 70 percent of the limit to the heap and leaves 30 percent for everything else. That is a sensible starting point for a typical Spring or Quarkus service. Services with many platform threads or heavy off-heap buffers may need 60 percent or lower.

If you hard-code -Xmx in an image, you have tied the image to one memory limit. A percentage travels with the container.

Fail loudly, not silently

-XX:+ExitOnOutOfMemoryError makes the JVM exit as soon as it hits an OutOfMemoryError, instead of limping on with broken threads. The orchestrator restarts it, and you get a clear error in the logs rather than a zombie that answers health checks but fails real requests.

Measure, then adjust

Do not guess at the non-heap part. Native Memory Tracking shows exactly where memory goes:

docker run -e JAVA_TOOL_OPTIONS="-XX:NativeMemoryTracking=summary" ... my-service
docker exec <container> jcmd 1 VM.native_memory summary

Run it under realistic load. Compare the committed total with the container limit and leave at least 10 to 15 percent of headroom. If metaspace or thread stacks dominate, that is a hint about your dependencies or your thread model, not just your settings.

Requests and limits in Kubernetes

In Kubernetes, set the memory request equal to the limit for JVM services. The JVM sizes itself from the limit, and if the request is lower, the scheduler may pack the node so tightly that the pod gets evicted under pressure. Memory is not compressible the way CPU is. 

resources:
  requests:
    memory: "1Gi"
    cpu: "500m"
  limits:
    memory: "1Gi"

A short checklist

  1. Use a container-aware JDK and a JRE base image.
  2. Replace -Xmx with -XX:MaxRAMPercentage, starting around 70.
  3. Add -XX:+ExitOnOutOfMemoryError.
  4. Measure with Native Memory Tracking under load and keep real headroom.
  5. In Kubernetes, set the memory request equal to the limit.

Exit code 137 should be a surprise once a year, not a weekly ritual.
