Structured events, correlation IDs, and the five fields every line should carry. ---

Every observability project I have joined started with tooling: a tracing backend, a metrics platform, a new dashboard. Every one of them eventually came back to the same unglamorous problem. When something broke, the first place people looked was the logs, and the logs could not answer the question. Traces and metrics are essential, but good logs are the foundation, and they are cheap to get right.

Log events, not sentences

A typical log line written for humans looks like this:

Order 8812 for customer 4410 failed after 3 retries because the payment service timed out

It reads well, but try answering "how many orders failed because of payment timeouts in the last hour?" You will be writing regular expressions. The same event as structured JSON is both readable and queryable: 

{
  "time": "2026-09-08T09:14:03.218Z",
  "level": "WARN",
  "service": "orders",
  "event": "order.failed",
  "order_id": "8812",
  "customer_id": "4410",
  "reason": "payment_timeout",
  "attempts": 3,
  "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736"
}

The event field is a stable name you can count and alert on. The reason is a fixed value, not free text. Everything else is context.

Five fields on every line

  1. time in UTC, with milliseconds.
  2. level, used consistently: ERROR means someone should look, WARN means it recovered.
  3. service and version, so you can compare old and new during a rollout.
  4. event, a dotted name like payment.captured.
  5. trace_id, so one request can be followed across services.

Correlation IDs, set once

The trace ID is what turns thousands of unrelated lines into a story. Set it once at the edge of the request and let the logging framework add it to every line, rather than passing it to every log call by hand. In Java, the Mapped Diagnostic Context does exactly this: 

public void handle(Request request, Response response) {
    String traceId = request.header("traceparent")
            .map(TraceIds::fromTraceparent)
            .orElseGet(TraceIds::random);
    MDC.put("trace_id", traceId);
    try {
        router.dispatch(request, response);
    } finally {
        MDC.remove("trace_id");
    }
}

With a JSON encoder configured, every log line written during that request carries the trace ID, including lines from libraries you did not write.

In containers, write to standard output

A container should not manage log files. Write one JSON object per line to standard output and let the platform collect it. docker logs works during development, and in Kubernetes the node's log agent ships everything to your log store without any configuration in the application. Log files inside a container fill the writable layer and disappear when the container is replaced, usually right when you need them. 

docker logs --since 10m orders-1 | jq 'select(.event == "order.failed") | .reason' | sort | uniq -c

What not to log

  • Secrets and personal data. Mask card numbers, tokens, and passwords at the source. Assume logs are read widely.
  • Every successful request at INFO. That is what access logs and metrics are for. Log what is interesting.
  • Stack traces for expected failures. A declined card is not an exception; it is an event with a reason.

Then add the rest

Once your logs are structured and correlated, metrics and traces slot in naturally: the same event names become counters, and the same trace IDs link a slow span to the log lines that explain it. Start with the log lines. They are the part of observability your team already reads every day.
