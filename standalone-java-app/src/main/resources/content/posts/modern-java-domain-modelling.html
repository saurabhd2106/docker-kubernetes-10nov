A payment example, from nullable fields to a model that cannot be wrong. ---

Most domain bugs I have debugged were not clever. They were a field that was supposed to be set only in some states, a status string with a typo, or a branch nobody wrote because nobody remembered the new case. Recent Java releases give us three tools that remove whole classes of these bugs: records, sealed interfaces, and pattern matching in switch. Used together, they let you model a domain so that illegal states do not compile.

The classic version

Here is a payment the way many of us wrote it ten years ago:

public class Payment {
    private String id;
    private String status;          // "PENDING", "CAPTURED", "FAILED", "REFUNDED"
    private BigDecimal amount;
    private Instant capturedAt;     // only set when CAPTURED or REFUNDED
    private String failureReason;   // only set when FAILED
    private BigDecimal refundedAmount;
    // getters, setters, equals, hashCode, toString...
}

Every comment is a rule the compiler cannot check. Nothing stops a FAILED payment with a capturedAt timestamp, or a status of "CAPTUERD".

One type per state

A sealed interface lists every state the payment can be in. Each state is a record that carries only the data that exists in that state: 

public sealed interface Payment
        permits Pending, Captured, Failed, Refunded {
    PaymentId id();
    Money amount();
}

public record Pending(PaymentId id, Money amount) implements Payment {}

public record Captured(PaymentId id, Money amount, Instant capturedAt) implements Payment {}

public record Failed(PaymentId id, Money amount, String reason) implements Payment {}

public record Refunded(PaymentId id, Money amount, Instant capturedAt, Money refunded)
        implements Payment {
    public Refunded {
        if (refunded.isGreaterThan(amount)) {
            throw new IllegalArgumentException("Cannot refund more than was captured");
        }
    }
}

Records give us immutability, equals, hashCode, and toString for free, and the compact constructor is the natural home for invariants. A failed payment simply has no capture time to get wrong.

Exhaustive switches

The real payoff comes when you handle the states. Because the interface is sealed, the compiler knows every implementation and can check that a switch covers them all: 

String describe(Payment payment) {
    return switch (payment) {
        case Pending _   -> "Waiting for the bank";
        case Captured c  -> "Paid on " + c.capturedAt();
        case Failed f    -> "Failed: " + f.reason();
        case Refunded r  -> "Refunded " + r.refunded() + " of " + r.amount();
    };
}

There is no default branch, and that is the point. When someone adds a Disputed state next quarter, every switch that does not handle it stops compiling. The compiler becomes the checklist.

Deconstruction patterns

Record patterns let you pull fields out right in the case label, guards let you split a case further, and the unnamed pattern _ says "I do not care about this part". Business rules end up reading like the rules people describe in meetings: 

Fee feeFor(Payment payment) {
    return switch (payment) {
        case Captured(_, Money amount, _) when amount.isAbove(Money.of("10000")) ->
            Fee.percent("0.9");
        case Captured _ -> Fee.percent("1.4");
        case Refunded _ -> Fee.fixed("0.30");
        case Pending _, Failed _ -> Fee.none();
    };
}

Transitions as functions

With immutable states, a transition is a method that takes one state and returns another. The method signature documents which transitions are legal: 

Captured capture(Pending pending, Clock clock) {
    return new Captured(pending.id(), pending.amount(), clock.instant());
}

Refunded refund(Captured captured, Money amount) {
    return new Refunded(captured.id(), captured.amount(), captured.capturedAt(), amount);
}

You cannot refund a pending payment because there is no method that accepts one. No status check, no exception, no test needed for that rule.

Where to be careful

  • Persistence. Map the sealed hierarchy to a table with a discriminator column at the edge of your system. Keep the database shape out of the domain types.
  • Serialization. Most JSON libraries support sealed types with a type property, but configure it explicitly and test the round trip.
  • Do not overdo it. A three-field value object does not need a sealed hierarchy. Use this where the states genuinely carry different data and different rules.

The result is code with fewer comments, fewer null checks, and fewer tests for impossible situations, because the impossible situations no longer exist.
