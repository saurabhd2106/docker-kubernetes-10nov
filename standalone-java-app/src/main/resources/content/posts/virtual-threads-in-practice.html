--- title: Virtual threads in practice: what changed in our HTTP services date: 2026-11-04 category: java tags: java, concurrency, performance, virtual threads author: priya cover: /images/covers/virtual-threads.svg summary: We moved forty blocking HTTP services to virtual threads. Throughput went up, thread pools went away, and three old habits turned into bugs. ---

For years, the rule for a blocking Java service was simple: size the thread pool carefully, because every request holds a platform thread while it waits on the database. Too few threads and requests queue. Too many and you pay for the memory and the context switches. Virtual threads remove that trade-off, and after moving forty of our HTTP services to them, I can report that the promise mostly holds. The surprises were in the code we had written around the old limits.

What a virtual thread actually is

A virtual thread is a java.lang.Thread that the JVM schedules, not the operating system. When it blocks on I/O, the JVM unmounts it from its carrier thread and parks its stack on the heap. The carrier is free to run another virtual thread straight away. A few carrier threads, one per CPU core by default, can serve tens of thousands of concurrent requests, each written in plain blocking style.

The switch in most of our services was one line:

// Before: a fixed pool we tuned by hand for every service
ExecutorService executor = Executors.newFixedThreadPool(200);

// After: one cheap virtual thread per task
ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor();

Frameworks made it even easier. Most now have a single property to run request handlers on virtual threads, so the majority of services changed configuration, not code.

The results

On services that spend most of their time waiting on other services, throughput under load rose by between 1.6 and 3 times, and p99 latency during traffic spikes fell sharply because requests stopped queueing for a free thread. CPU-bound services saw no change, which is exactly what you should expect: virtual threads make waiting cheap, not computing faster.

Virtual threads are not faster threads. They are cheaper threads, so you can afford one for every task that waits.

Three habits that turned into bugs

1. Pooling virtual threads

Old instincts die hard. One team wrapped virtual threads in a fixed-size pool "to be safe". That brings back the queueing that virtual threads remove. Never pool them. If you need to limit concurrency against a fragile downstream, limit the downstream call, not the threads: 

private final Semaphore inventoryPermits = new Semaphore(20);

Stock checkStock(String sku) throws InterruptedException {
    inventoryPermits.acquire();
    try {
        return inventoryClient.stockFor(sku);
    } finally {
        inventoryPermits.release();
    }
}

2. Expensive objects in ThreadLocal

We cached date formatters and JSON buffers in ThreadLocal, which made sense when there were 200 long-lived threads. With a new virtual thread per request, each request built its own cache and threw it away. Heap churn went up noticeably. The fix was to share immutable objects such as DateTimeFormatter and to stop caching mutable ones per thread.

3. Long blocking calls inside synchronized

Early versions of virtual threads could pin the carrier thread when blocking inside a synchronized block, which quietly capped concurrency at the number of cores. Recent JDKs fixed most pinning for synchronized, but native calls and some older drivers can still pin. Run a load test with -Djdk.tracePinnedThreads=full on older runtimes, or watch the jdk.VirtualThreadPinned JFR event, before you declare victory.

Connection pools still matter

Ten thousand virtual threads can all try to borrow a database connection at once. Your pool of 30 connections did not grow just because threads got cheap. In practice the connection pool became our real concurrency limit, which is healthier than an arbitrary thread count, but it means pool timeouts now need sensible values and clear errors.

Should you switch?

If your service is a classic request-response app that spends its time waiting on databases and other services, yes. Start with one service, load test it, look for pinning and ThreadLocal abuse, and keep the connection pool honest. If your code is already fully reactive and working well, there is no urgency to rewrite it. The real win of virtual threads is that new code can stay simple.
