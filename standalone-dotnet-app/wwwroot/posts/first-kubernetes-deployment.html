From docker run to your first Kubernetes Deployment

If you can run a container with Docker, you already understand most of a Deployment manifest. It just has more words. We translate one command into YAML, flag by flag, and then let Kubernetes do the things Docker cannot.

Priya Nair November 3, 2026 · 5 min read

Here is the command we have been using to run this blog:

docker run -d --name blog --restart=always -p 8080:8080 -e PORT=8080 blog-dotnet:1.0

It works, on one machine, for one copy. If the machine dies, so does the blog. If you want three copies, you run the command three times and pick three host ports. Kubernetes takes the same container and asks a different question. Instead of "run this", you tell it "make sure this is always running, this many times".

Step 0: get the image where the cluster can see it

The cluster pulls images itself; it cannot see the images on your laptop. For a real cluster, push to a registry. For a local cluster, load the image directly: 

docker build -t blog-dotnet:1.0 .

kind load docker-image blog-dotnet:1.0       # kind
minikube image load blog-dotnet:1.0          # minikube
# Docker Desktop's built-in cluster can use local images directly
Avoid :latest here

For images tagged :latest, Kubernetes defaults to imagePullPolicy: Always, tries to pull from Docker Hub, and fails with ErrImagePull for an image that only exists locally. A real version tag such as 1.0 avoids that, and makes rollbacks meaningful.

Step 1: the Deployment

apiVersion: apps/v1
kind: Deployment
metadata:
  name: blog
  labels:
    app: blog
spec:
  replicas: 3
  selector:
    matchLabels:
      app: blog
  template:
    metadata:
      labels:
        app: blog
    spec:
      securityContext:
        runAsNonRoot: true
        runAsUser: 1654
      containers:
        - name: blog
          image: blog-dotnet:1.0
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 8080
          env:
            - name: PORT
              value: "8080"
          resources:
            requests:
              cpu: 100m
              memory: 128Mi
            limits:
              memory: 256Mi

Three parts of this are worth slowing down for.

The template is a pod

Everything under template describes one pod: the containers, their environment, and their security settings. The Deployment's job is to keep replicas copies of that pod running. If you change the template, it rolls out new pods to replace the old ones.

Labels are the glue

Kubernetes objects do not hold direct references to each other. The Deployment finds its pods by label selector: any pod labelled app: blog is one of its own. The template stamps that label on every pod it creates, and selector.matchLabels must match it. The Service we create next uses the same trick.

Requests are a promise, limits are a wall

requests tell the scheduler how much room to reserve on a node. The memory limit is enforced: exceed it and the container is OOM-killed. .NET reads the container's memory limit and sizes its garbage collector heap to fit, so set it to something realistic rather than leaving it unlimited. 

kubectl apply -f deployment.yaml
kubectl get pods -l app=blog

Step 2: the Service

Pods come and go, and each one has its own IP address. A Service gives the set of them one stable name and address, and load-balances across whichever pods currently match its selector: 

apiVersion: v1
kind: Service
metadata:
  name: blog
spec:
  selector:
    app: blog
  ports:
    - port: 80
      targetPort: 8080

Inside the cluster, any pod can now reach the blog at http://blog. The Service listens on port 80 and forwards to the pods' targetPort 8080, which is the same host-to-container split as -p.

Step 3: see the load balancing

The quickest way to open it in a browser is kubectl port-forward svc/blog 8080:80. One surprise: port-forward picks one pod and sticks with it, so refreshing always shows the same hostname in the footer. To see traffic actually spread across replicas, call the Service from inside the cluster: 

kubectl run curl --rm -it --image=curlimages/curl -- \
  sh -c 'for i in 1 2 3 4 5 6; do curl -s http://blog/ | grep -o "Served by <code>[^<]*"; done'

You will see the three pod names rotate through the output.

Step 4: the things Docker could not do

Self-healing. Delete a pod and watch a replacement appear within seconds:

kubectl delete pod blog-7c9f8d6b5d-q8m2n
kubectl get pods -l app=blog -w

Scaling. One command, no port juggling:

kubectl scale deployment/blog --replicas=5

Rolling updates. Build blog-dotnet:1.1, load it, and point the Deployment at it. Kubernetes replaces pods a few at a time, so the blog never goes fully down: 

kubectl set image deployment/blog blog=blog-dotnet:1.1
kubectl rollout status deployment/blog
kubectl rollout undo deployment/blog      # if 1.1 is bad

What is still missing

Right now Kubernetes considers a pod ready the moment its process starts, and it only restarts a pod whose process exits. That is the same blind spot Docker had before we added a health check. The fix is probes, and choosing the right kind matters more than it seems. That is the subject of Liveness vs readiness.
