Liveness vs readiness: two questions Kubernetes asks your app

"Should I restart you?" and "Should I send you traffic?" sound similar. Answer the wrong one and a slow database turns into a cluster-wide restart loop. Here is how we set up probes for ASP.NET Core.

Aisha Khan November 6, 2026 · 5 min read

The incident review read like this. At 14:02 the primary database had a failover that took about forty seconds. At 14:03 every pod of the orders service was restarting. At 14:09 the database was healthy, but the service was still down, because forty pods booting at once were hammering it with connection attempts and warm-up queries. The root cause was not the database. It was one line in a probe.

Three probes, three different consequences

Kubernetes runs probes from the kubelet on each node. They can be HTTP requests, TCP connects, gRPC calls or commands. What matters is what happens when they fail:

ProbeQuestionOn failure
startupHave you finished starting?Keep waiting, up to the threshold, then restart. Other probes are paused until it passes.
livenessAre you stuck beyond repair?Restart the container.
readinessCan you take requests right now?Remove the pod from Service endpoints. No restart.

Readiness failures are cheap and reversible: the pod stops getting traffic and gets it back as soon as the probe passes again. Liveness failures are drastic: the process is killed, in-memory state is lost, and the app has to start from cold.

What went wrong in our incident

The orders service had one /health endpoint that also checked the database connection, and it was wired to both probes. When the database blinked, liveness failed on every replica at the same moment, and Kubernetes did exactly what it was told: it restarted all of them.

A liveness probe should only fail when restarting the container would fix the problem.

Restarting your app does not fix a database failover. It just adds a stampede of cold starts on top of one. The dependency check belonged in readiness, where failing would have quietly taken pods out of rotation and put them back forty seconds later.

Probes for this blog

This blog has no dependencies, so its /health endpoint only proves that Kestrel is accepting requests and the pipeline is moving. That is a correct liveness check and a reasonable readiness check, so it serves both: 

containers:
  - name: blog
    image: blog-dotnet:1.0
    ports:
      - containerPort: 8080
    startupProbe:
      httpGet: { path: /health, port: 8080 }
      periodSeconds: 2
      failureThreshold: 30        # up to 60s to start
    livenessProbe:
      httpGet: { path: /health, port: 8080 }
      periodSeconds: 10
      timeoutSeconds: 2
      failureThreshold: 3         # 30s stuck, then restart
    readinessProbe:
      httpGet: { path: /health, port: 8080 }
      periodSeconds: 5
      timeoutSeconds: 2
      failureThreshold: 2

A few of those numbers are deliberate:

  • The startup probe replaces initialDelaySeconds. Instead of guessing how long startup takes, it polls quickly and lets liveness take over as soon as the app is up.
  • timeoutSeconds defaults to 1. One slow garbage collection pause can exceed that. We set 2 seconds explicitly.
  • Liveness is slower to give up than readiness. Stop sending traffic quickly, but restart reluctantly.

Real apps: separate endpoints with ASP.NET Core health checks

Once you have dependencies, split the endpoints. ASP.NET Core's built-in health checks support tags, and each endpoint can choose which checks it runs: 

builder.Services.AddHealthChecks()
    .AddCheck<DatabaseHealthCheck>("database", tags: ["ready"])
    .AddCheck<CacheHealthCheck>("cache", tags: ["ready"]);

var app = builder.Build();

// Liveness: run no checks at all. Answering proves the process is responsive.
app.MapHealthChecks("/healthz/live", new HealthCheckOptions { Predicate = _ => false });

// Readiness: only the checks tagged "ready".
app.MapHealthChecks("/healthz/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready")
});

Point livenessProbe at /healthz/live and readinessProbe at /healthz/ready. Keep each dependency check fast, and give it its own short timeout, so that a hanging dependency makes readiness fail rather than time out.

Readiness during shutdown

When a pod is deleted during a rollout, two things happen in parallel: the container gets SIGTERM, and the pod is removed from Service endpoints. Removal takes a moment to reach every node, so for a second or two traffic can still arrive at a pod that is shutting down.

ASP.NET Core handles SIGTERM gracefully: it stops accepting new connections and waits for in-flight requests, by default for up to 30 seconds in recent versions. To cover the propagation gap, add a short pause before shutdown begins. Chiseled images have no sleep binary, so use the built-in sleep action available in recent Kubernetes versions: 

lifecycle:
  preStop:
    sleep:
      seconds: 5

Keep terminationGracePeriodSeconds, which also defaults to 30, longer than the pre-stop pause plus your shutdown timeout.

Mistakes we have made so you do not have to

  • Dependency checks in liveness. The incident above.
  • The same aggressive settings for every probe. Liveness that gives up after five seconds will restart pods during every long GC pause or CPU throttle.
  • Probes that need authentication. The kubelet sends no credentials. A 401 counts as a failure.
  • Expensive probes. A probe that runs a real query every five seconds, on fifty pods, is real load. Cache the result for a few seconds if the check is costly.
  • No readiness probe at all. Then a pod receives traffic the instant its process starts, before it has warmed up.
Try it

Apply the probes above, then run kubectl describe pod on one of the blog pods. The Liveness, Readiness and Startup lines show exactly what the kubelet is checking, and the Events section records every probe failure.
