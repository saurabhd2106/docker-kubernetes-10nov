A production Dockerfile for ASP.NET Core, line by line

The Dockerfile you write in five minutes works. It is also huge, runs as root, re-downloads every NuGet package on each build and ignores shutdown signals. Here is the version we actually ship, and why each line is there.

Marco Silva October 15, 2026 · 6 min read

The five-minute version

Almost everyone's first ASP.NET Core Dockerfile looks something like this:

FROM mcr.microsoft.com/dotnet/sdk:10.0
WORKDIR /src
COPY . .
RUN dotnet publish -c Release -o /app
ENTRYPOINT ["dotnet", "/app/Blog.dll"]

It builds and it runs. It also has four problems that only show up later:

  • It ships the whole SDK. Compilers, NuGet, MSBuild and your source code all end up in production, which means several hundred megabytes of extra download and attack surface.
  • Every change re-restores. COPY . . comes before the restore, so editing one line of CSS invalidates the cache and downloads every package again.
  • It runs as root. If the app is compromised, the attacker is root inside the container.
  • It drags in local junk. Your bin/ and obj/ folders get copied into the build, and stale obj/ files can break the restore in confusing ways.

The version we ship

This is the Dockerfile this blog is built with:

# syntax=docker/dockerfile:1

# ---- Stage 1: publish the app with the full .NET SDK ----
FROM mcr.microsoft.com/dotnet/sdk:10.0 AS build
WORKDIR /src

COPY Blog.csproj ./
RUN dotnet restore

COPY . .
RUN dotnet publish -c Release -o /app/publish --no-restore -p:UseAppHost=false

# ---- Stage 2: run the app on the slimmer ASP.NET Core runtime ----
FROM mcr.microsoft.com/dotnet/aspnet:10.0
WORKDIR /app

COPY --from=build /app/publish ./

ENV PORT=8080 \
    ASPNETCORE_HTTP_PORTS=
EXPOSE 8080
USER app

HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD ["dotnet", "/app/Blog.dll", "--healthcheck"]

ENTRYPOINT ["dotnet", "/app/Blog.dll"]

Let's take it from the top.

Two stages, two jobs

A multi-stage build uses more than one FROM. Each stage starts from a clean base, and only what you explicitly COPY --from an earlier stage carries forward. The build stage has everything needed to compile. The final stage starts again from mcr.microsoft.com/dotnet/aspnet, which contains the .NET and ASP.NET Core runtimes and nothing else, and copies in only the published output.

The SDK stage never ships. Run docker image ls after a build and compare the SDK image with the final image to see how much that saves.

The restore layer that actually caches

COPY Blog.csproj ./
RUN dotnet restore

COPY . .

Docker caches each layer and reuses it as long as the instruction and its input files are unchanged. By copying only the project file first, the expensive dotnet restore layer depends only on your package references. Day-to-day code edits invalidate the COPY . . layer below it, and the restore comes straight from cache.

Real solutions have more than one project. Copy every file that affects restore before running it: each .csproj, plus Directory.Build.props, Directory.Packages.props and NuGet.config if you use them. 

COPY Directory.Packages.props NuGet.config ./
COPY src/Blog.Web/Blog.Web.csproj src/Blog.Web/
COPY src/Blog.Core/Blog.Core.csproj src/Blog.Core/
RUN dotnet restore src/Blog.Web/Blog.Web.csproj
Going further: a NuGet cache mount

With BuildKit you can keep the NuGet package folder between builds, even when the restore layer is invalidated: RUN --mount=type=cache,id=nuget,target=/root/.nuget/packages dotnet restore. Adding one package then downloads one package, not all of them.

.dockerignore is part of the build

COPY . . copies the whole build context, which is the directory you pass to docker build. A .dockerignore file keeps things out of it: 

bin/
obj/
.git/
.vs/
.vscode/
*.user

Excluding obj/ matters more than it looks. It contains project.assets.json with paths from your machine. If it sneaks into the image, a --no-restore publish can pick up stale assets and fail with errors that only happen in CI.

Publish flags

  • -c Release builds optimized code.
  • --no-restore reuses the cached restore layer instead of restoring again.
  • -p:UseAppHost=false skips the native launcher executable. We start the app with dotnet Blog.dll, so it is not needed.

Run as a normal user

Since .NET 8, every official Linux image ships a non-root user called app with UID 1654. Switching to it takes one line, USER app. Files copied with COPY stay owned by root, so the app can read its own binaries but cannot modify them. That is exactly what you want.

Kubernetes' runAsNonRoot check can only verify a numeric user. The images expose the UID as an environment variable, so USER $APP_UID gives you the same user in a form the check accepts.

Ports and the health check

The ASP.NET Core images listen on port 8080 by default, which is unprivileged and so works without root. This app reads PORT instead, for consistency across our samples. The details are in Port mapping, or why localhost:8080 works. The HEALTHCHECK uses an in-process probe because the runtime image has no curl, which we cover in Health checks: is it running, or is it working?.

Exec form ENTRYPOINT, or why shutdown takes ten seconds

Compare these two lines:

ENTRYPOINT ["dotnet", "/app/Blog.dll"]   # exec form
ENTRYPOINT dotnet /app/Blog.dll          # shell form

The shell form runs your app as a child of /bin/sh -c. The shell becomes PID 1 and does not forward SIGTERM to it. docker stop waits ten seconds and then kills everything, so in-flight requests are cut off. With the exec form, dotnet is PID 1, receives SIGTERM directly, and ASP.NET Core drains requests and shuts down cleanly.

Pick your tag on purpose

Building for more than one CPU

Laptops are increasingly ARM and many clusters are still x64. docker buildx can produce one image tag that works on both: 

docker buildx build --platform linux/amd64,linux/arm64 -t registry.example.com/blog:1.0 --push .

For faster builds, run the SDK stage natively with FROM --platform=$BUILDPLATFORM and pass -a $TARGETARCH to dotnet publish, so that only the small runtime stage is emulated.

Checklist

  • Multi-stage build: SDK to build, aspnet to run.
  • Project files copied and restored before the source.
  • .dockerignore excludes bin/, obj/ and .git/.
  • Runs as app, or $APP_UID for Kubernetes.
  • Exec form ENTRYPOINT.
  • A health check that works without curl.
  • A tag strategy you chose, not one you inherited.

Once this is in place, the next question is usually "can it be smaller?". It can, and we measured how much.
