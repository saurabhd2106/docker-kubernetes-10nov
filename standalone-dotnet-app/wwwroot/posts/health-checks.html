Health checks: is it running, or is it working?

Docker knows whether your process is alive. It has no idea whether that process is answering requests. A health check closes the gap, even in a runtime image with no curl.

Aisha Khan October 22, 2026 · 4 min read

Here is a failure I have been paged for more than once. The container is Up 3 days. The process is running. CPU is flat. And every request has been timing out since 2 a.m., because a thread pool is exhausted or a deadlock has the request pipeline stuck. From Docker's point of view, nothing is wrong. The main process has not exited, so the container is "running".

A health check asks a better question: not "is the process alive?" but "can it do its job?". This blog ships with one, and it is worth walking through how it works because the runtime image makes it slightly less obvious than the documentation suggests.

Step one: an endpoint worth asking

The app exposes /health, which returns 200 OK with the body ok:

app.MapGet("/health", () => Results.Text("ok\n", "text/plain; charset=utf-8"));
curl -i http://localhost:8080/health

It looks trivial, and it is meant to. If this endpoint answers, Kestrel is accepting connections, the request pipeline is moving, and the thread pool has room to run a handler. That is exactly the set of things that break in the 2 a.m. scenario above.

Step two: tell Docker about it

The Dockerfile declares the check:

HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD ["dotnet", "/app/Blog.dll", "--healthcheck"]
OptionMeaning
--interval=30sRun the check every 30 seconds.
--timeout=5sA check that takes longer than 5 seconds counts as a failure.
--start-period=10sFailures in the first 10 seconds do not count, which gives the app time to start.
--retries=3Three consecutive failures mark the container unhealthy.

Docker only looks at the exit code of the command: 0 means healthy and 1 means unhealthy.

Step three: checking without curl

Almost every health check example uses curl -f http://localhost/health || exit 1. The mcr.microsoft.com/dotnet/aspnet images do not include curl or wget, and the chiseled variants do not even have a shell to run that ||. You could install curl, but that adds weight and attack surface to every image just to make one HTTP call.

Instead, the app checks itself. When it is started with --healthcheck, it skips starting the web server, calls its own /health endpoint, and exits: 

if (args.Contains("--healthcheck"))
{
    return await HealthCheck.RunAsync(port);
}

public static async Task<int> RunAsync(int port)
{
    using var client = new HttpClient { Timeout = TimeSpan.FromSeconds(2) };
    try
    {
        using var response = await client.GetAsync($"http://127.0.0.1:{port}/health");
        return response.StatusCode == HttpStatusCode.OK ? 0 : 1;
    }
    catch (Exception e)
    {
        Console.Error.WriteLine($"Health check failed: {e.Message}");
        return 1;
    }
}

Note the exec form in the Dockerfile: ["dotnet", "/app/Blog.dll", "--healthcheck"]. It runs the binary directly instead of going through /bin/sh -c, so it works the same way on images that have no shell at all.

Watching the states change

A container with a health check moves through three states:

  1. starting: within the start period, before the first check passes.
  2. healthy: the most recent check passed.
  3. unhealthy: retries checks in a row have failed.
docker run -d --name blog-1 -p 8080:8080 blog-dotnet
docker ps --format '{{.Names}}  {{.Status}}'
blog-1  Up 4 seconds (health: starting)
blog-1  Up 41 seconds (healthy)

For scripts, ask for just the state, or look at the last few results with their output:

docker inspect --format '{{.State.Health.Status}}' blog-1
docker inspect --format '{{json .State.Health.Log}}' blog-1
Unhealthy does not mean restarted

Plain Docker only reports health. It will not restart an unhealthy container, even with --restart=always, which reacts to the process exiting. Docker Compose can use health to order startup with depends_on: condition: service_healthy, and orchestrators act on it, but on a single host something else has to be watching.

Keep the check cheap and honest

A few rules we follow for every service:

  • No heavy work. The check runs every 30 seconds for the life of the container. It should take milliseconds.
  • Check the process, not the world. If /health fails whenever the database is slow, a database blip marks every instance unhealthy at once. Dependency checks belong in a readiness check, not a liveness check.
  • Do not require authentication. The checker has no credentials, and it should not need any.

Looking ahead to Kubernetes

Kubernetes ignores the Dockerfile HEALTHCHECK entirely. It uses its own liveness, readiness and startup probes, configured in the pod spec. The good news is that the same /health endpoint plugs straight in. The difference between those probes matters a lot, which is why it gets a post of its own.
