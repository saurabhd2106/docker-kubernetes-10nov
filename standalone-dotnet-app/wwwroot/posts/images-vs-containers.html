Images vs containers: the recipe and the meal

The two words get used interchangeably, but they are different things with different lifetimes. Getting the distinction right makes almost everything else about Docker easier to reason about.

Priya Nair October 1, 2026 · 5 min read

An image is a recipe. It is a read-only package that contains a filesystem and a little metadata describing how to run it. A container is the meal: a running process started from that image, with its own writable scratch space on top. You can cook the same recipe as many times as you like, and burning one meal does nothing to the recipe card.

That sounds like a definition you can skim past. In practice, most early container confusion comes from mixing the two up: editing files inside a running container and expecting the image to change, or rebuilding an image and expecting running containers to pick it up.

What is actually inside an image

An image has two parts:

  • A stack of filesystem layers. Each layer is a tarball of file changes: files added, changed or deleted.
  • A config document. This holds the default command, environment variables, the working directory, the user to run as and the ports the app expects to use.

You can look at the config of this blog's image directly:

docker image inspect blog-dotnet \
  --format '{{json .Config.Entrypoint}} {{.Config.User}} {{json .Config.ExposedPorts}}'

You will see the dotnet /app/Blog.dll entrypoint, the app user and port 8080. Nothing in there is running yet. It is just a description.

Layers, and why order matters

Every COPY, ADD and RUN instruction in a Dockerfile produces a new layer. Layers are content-addressed: each one is identified by a hash of its contents. That has two big consequences.

  1. Layers are shared. Ten images built on mcr.microsoft.com/dotnet/aspnet:10.0 store the base layers on disk once and pull them over the network once.
  2. Layers are cached. If an instruction and its inputs have not changed, Docker reuses the previous layer instead of running the step again.

The second point is why our Dockerfile copies Blog.csproj and runs dotnet restore before copying the rest of the source. Editing a page invalidates the layer that copies the source, but the restore layer above it is untouched and comes straight from cache. 

docker history blog-dotnet

docker history lists the layers newest first, with the instruction that created each one and its size. The large layers at the bottom come from the base image. The few small ones at the top are ours.

One image, many containers

Build once, then start as many copies as you need:

docker build -t blog-dotnet .
docker run -d --name blog-1 -p 8080:8080 blog-dotnet
docker run -d --name blog-2 -p 8081:8080 blog-dotnet

Both containers come from the same image, yet each has its own hostname, its own process tree and its own network address. Open localhost:8080 and localhost:8081 and compare the footers: the hostname is the container ID, and it differs on each.

The writable layer

When Docker starts a container, it stacks one thin, empty, writable layer on top of the image's read-only layers. Any file the process creates or modifies lands there. This is copy-on-write: when a file from the image is modified, it is first copied up into the writable layer and changed there, and the original stays untouched underneath. 

docker exec blog-1 sh -c 'echo hello > /tmp/hello.txt'
docker diff blog-1
C /tmp
A /tmp/hello.txt

A means added and C means changed. Run docker diff blog-2 and you will see nothing: the second container never saw that file, because its writable layer is separate.

Containers are disposable

docker rm blog-1 deletes the writable layer along with everything in it. Anything that must outlive the container, such as uploads, databases or logs you care about, belongs in a volume or an external service, not in the container's filesystem.

Tags are names, digests are identities

blog-dotnet:latest and aspnet:10.0 are tags. A tag is a movable pointer, a bit like a Git branch. Microsoft republishes aspnet:10.0 every time a patch release or a base OS security fix comes out, so pulling the same tag next month gives you different bytes.

A digest such as sha256:4f1c… is the hash of the image manifest itself. It can never point at anything else. That is the right reference when you need a build to be exactly reproducible: 

FROM mcr.microsoft.com/dotnet/aspnet:10.0@sha256:<digest>

Most teams pin a tag in day-to-day Dockerfiles and let a bot such as Dependabot or Renovate bump digests through pull requests. That way updates are deliberate and reviewed instead of silent.

The mental model to keep

Images are built, versioned and shipped. Containers are started, stopped and thrown away.

If you want a change to survive, change the Dockerfile or the source and build a new image. If you want more capacity, start more containers from the same image. Kubernetes takes exactly this idea and automates it, which is where we pick up in From docker run to your first Kubernetes Deployment.

Try it

Run docker image ls blog-dotnet and then docker image ls mcr.microsoft.com/dotnet/sdk. The difference in size is everything the multi-stage build left behind.
