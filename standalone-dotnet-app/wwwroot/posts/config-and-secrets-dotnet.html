Configuration and secrets for .NET on Kubernetes

Build the image once and configure it everywhere. ASP.NET Core's configuration system was made for this, as long as you know how its layers stack up and keep your secrets out of the image.

Priya Nair November 9, 2026 · 5 min read

The rule that makes containers work across environments is simple: the same image runs in dev, staging and production. You do not rebuild for production. Everything that differs between environments, such as connection strings, feature flags, log levels and API keys, has to come from outside the image at runtime.

How ASP.NET Core stacks configuration

WebApplication.CreateBuilder sets up configuration sources in a fixed order. Every source can override keys from the sources before it, so the last one wins:

  1. appsettings.json
  2. appsettings.{Environment}.json, for example appsettings.Production.json
  3. User secrets, in the Development environment only
  4. Environment variables
  5. Command-line arguments

Defaults live in appsettings.json inside the image. Environment variables, which are easy to set from Docker and Kubernetes, override them. The environment name itself comes from ASPNETCORE_ENVIRONMENT, and defaults to Production when it is not set.

The double underscore

Configuration keys are hierarchical. In JSON, that is nesting:

{
  "Blog": {
    "Title": "Container Field Notes",
    "PostsPerPage": 9
  }
}

Internally, the key is Blog:Title. Colons are not allowed in environment variable names on every platform, so the environment variable provider maps a double underscore to the separator instead: 

docker run -e Blog__Title="Field Notes (staging)" -e Blog__PostsPerPage=5 blog-dotnet

Blog__Title becomes Blog:Title and overrides the JSON value. Arrays use indexes: AllowedOrigins__0, AllowedOrigins__1. Lookups are case-insensitive, so BLOG__TITLE works too.

Bind it once, validate it at startup

Reading strings from configuration all over the codebase gets messy. Bind a section to a class instead:

public sealed class BlogOptions
{
    [Required] public string Title { get; set; } = "";
    [Range(1, 50)] public int PostsPerPage { get; set; } = 9;
}

builder.Services.AddOptions<BlogOptions>()
    .Bind(builder.Configuration.GetSection("Blog"))
    .ValidateDataAnnotations()
    .ValidateOnStart();

ValidateOnStart is the important line. A typo in a variable name now crashes the pod at startup, with a clear error in kubectl logs, instead of surfacing as a strange bug three hours later. Kubernetes shows that as CrashLoopBackOff, and the rollout stops before it replaces your healthy pods.

ConfigMaps: non-secret settings

A ConfigMap holds plain key-value configuration. You can inject all of its keys as environment variables:

apiVersion: v1
kind: ConfigMap
metadata:
  name: blog-config
data:
  ASPNETCORE_ENVIRONMENT: Production
  Blog__Title: Container Field Notes
  Blog__PostsPerPage: "9"
  Logging__LogLevel__Default: Warning
---
# in the Deployment's container spec
envFrom:
  - configMapRef:
      name: blog-config

Secrets: the things that must not leak

First, where secrets must not go:

Never bake secrets into the image

ENV ConnectionStrings__Db=... in a Dockerfile, a COPY of appsettings.Production.json with a password in it, and --build-arg values all end up readable by anyone who can pull the image, through docker history or docker inspect. Deleting the file in a later layer does not remove it from earlier ones. If a build step genuinely needs a secret, such as a private NuGet feed token, use a BuildKit secret mount: RUN --mount=type=secret,id=nuget ....

At runtime, a Kubernetes Secret looks a lot like a ConfigMap:

apiVersion: v1
kind: Secret
metadata:
  name: blog-secrets
type: Opaque
stringData:
  ConnectionStrings__Db: "Host=db;Database=blog;Username=blog;Password=change-me"
---
env:
  - name: ConnectionStrings__Db
    valueFrom:
      secretKeyRef:
        name: blog-secrets
        key: ConnectionStrings__Db

In practice you would create that Secret with kubectl create secret or a secrets operator, not commit it to Git. Know what a Secret does and does not give you, too. Values are base64-encoded, not encrypted. The real protection is RBAC that limits who can read Secrets, and encryption at rest configured for the cluster's datastore. Many teams go one step further and keep secrets in a dedicated store such as Azure Key Vault, AWS Secrets Manager or HashiCorp Vault, syncing them into the cluster with the External Secrets Operator or the Secrets Store CSI driver.

Environment variables or files?

Environment variables are simple, but they are fixed when the container starts and can show up in crash dumps and debug output. Mounting a Secret as files avoids both problems: 

volumes:
  - name: secrets
    secret:
      secretName: blog-secrets
containers:
  - name: blog
    volumeMounts:
      - name: secrets
        mountPath: /run/secrets/blog
        readOnly: true

Each key becomes a file named after the key. ASP.NET Core's key-per-file provider reads a directory like that straight into configuration, and file names use the same double underscore convention: 

builder.Configuration.AddKeyPerFile("/run/secrets/blog", optional: true);

Mounted files are also updated in place when the Secret changes. Environment variables never are: changing a ConfigMap or Secret used through env has no effect until the pods restart, which kubectl rollout restart deployment/blog does gracefully.

Checklist

Kind of settingWhere it lives
Sensible defaultsappsettings.json in the image
Per-environment, non-secretConfigMap, through envFrom
Passwords, tokens, keysSecret, ideally mounted as files and synced from a vault
Build-time credentialsBuildKit secret mounts, never ENV or ARG
Typos and missing valuesCaught by ValidateOnStart

This blog only needs one setting, PORT, which makes it a nice minimal example of the same idea. The image is identical everywhere, and the environment decides how it runs.
