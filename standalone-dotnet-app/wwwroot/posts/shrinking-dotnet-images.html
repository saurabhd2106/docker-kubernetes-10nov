Shrinking .NET container images: Alpine, chiseled and Native AOT

We took this blog, built it five different ways and measured the results. Going from 963 MB to 42 MB is very achievable, but every step down trades away something. Here is the menu, with prices.

Marco Silva October 29, 2026 · 5 min read

Image size is not a vanity metric. Smaller images pull faster when a node scales up or a pod moves. They cost less to store and replicate across regions. Most importantly, they contain fewer packages, and every package you do not ship is a CVE you will never have to patch. But the smallest options also remove tools you may be used to having, so it is worth knowing exactly what you give up.

The results

Same source code and same Dockerfile structure, with only the base image and publish options changed. Sizes are uncompressed, as reported by docker image ls on an arm64 machine, using .NET 10.0.14 images. Registry download sizes are smaller because layers are compressed.

Our app contributes well under a megabyte to each of these. Almost all of the size is the base image, which is why choosing the base is the single biggest lever you have.

Step 1: stop shipping the SDK

This is the free win. A multi-stage build compiles in the SDK image and copies the output into aspnet. It cuts more than 700 MB and costs nothing. If you have not done this yet, start with our production Dockerfile walkthrough.

Step 2: Alpine

Change one line and the image halves:

FROM mcr.microsoft.com/dotnet/aspnet:10.0-alpine

Alpine uses musl instead of glibc. Pure managed code does not care, and .NET publishes musl builds of the runtime. Where it can bite is native dependencies: a NuGet package that ships a glibc-only .so, or a library that loads system ICU or fonts. Also note that the Alpine images run in globalization-invariant mode by default. Culture-specific formatting falls back to invariant unless you install icu-libs and turn invariant mode off.

Step 3: chiseled

FROM mcr.microsoft.com/dotnet/aspnet:10.0-noble-chiseled

Chiseled images are Ubuntu with everything removed except the files .NET needs: no shell, no package manager, no coreutils. They are about the same size as Alpine here, but they keep glibc, so native libraries built for Ubuntu work unchanged. They also default to the non-root app user. Like Alpine, they run in globalization-invariant mode. If you need full culture support, use the 10.0-noble-chiseled-extra variant, which adds ICU and time zone data.

The trade-off is that you cannot shell into them:

docker exec -it blog-1 sh
exec: "sh": executable file not found in $PATH

That is a feature in production and a surprise the first time you need to debug. Shell-form RUN and HEALTHCHECK instructions fail for the same reason, which is why this blog's health check is an exec-form command handled by the app itself.

Debugging without a shell

In Kubernetes, kubectl debug -it pod/blog-xyz --image=busybox --target=blog attaches a temporary container that shares the pod's process namespace, so you get your tools without baking them into the image.

Step 4: self-contained and trimmed

Framework-dependent apps need the whole shared framework present. A self-contained publish bundles the runtime with the app instead, and trimming removes the framework code the app never calls. The result can run on runtime-deps, which contains only the native libraries .NET itself depends on (12.6 MB for the chiseled variant). 

RUN dotnet publish -c Release -r linux-arm64 --self-contained \
      -p:PublishTrimmed=true -o /app/publish

FROM mcr.microsoft.com/dotnet/runtime-deps:10.0-noble-chiseled
COPY --from=build /app/publish /app
ENTRYPOINT ["/app/Blog"]

That took this blog from 132 MB to 42 MB. What it costs:

  • An architecture-specific build. You now publish per runtime identifier (linux-x64, linux-arm64), so multi-arch images need a build per platform.
  • Trimming can break reflection. Code that discovers types at runtime, such as some serializers, DI scanning or MVC, may lose the members it needs. Treat every trim warning as a bug. Our app is a few hundred lines of minimal APIs, which is the easy case.
  • You own runtime patching. The runtime is inside your app layer, so a .NET security patch means rebuilding the app, not just pulling a new base image.

Step 5: Native AOT

Native AOT compiles the app ahead of time into a single native executable with no JIT. Images get smaller still, and startup drops to tens of milliseconds, which matters for scale-to-zero and serverless workloads. The constraints are stricter than trimming: no runtime code generation, a restricted set of ASP.NET Core features (minimal APIs and gRPC work, MVC and Razor do not), and source-generated JSON serialization. The SDK image also needs the native toolchain (clang and friends) to build it. For a new, small API service, it is worth trying. For an existing MVC app, it is usually a rewrite.

What we actually use

SituationOur default
Most ASP.NET Core servicesaspnet:10.0-noble-chiseled
Need a shell or apt packages at runtimeaspnet:10.0
Small minimal-API services, size or cold start mattersTrimmed or AOT on runtime-deps chiseled
Training and demos (this blog)aspnet:10.0, so people can docker exec in and look around

Start with chiseled. Move up to the full image when you need a tool, or down to trimmed when you need the bytes.

Try it yourself: change the runtime FROM line in this blog's Dockerfile, rebuild, and compare with docker image ls.
