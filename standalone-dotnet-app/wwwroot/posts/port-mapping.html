Port mapping, or why localhost:8080 works

Your app is listening. Docker says the container is up. The browser says "connection refused". Here is what sits between the two, and the three settings that have to agree.

Marco Silva October 8, 2026 · 4 min read

Inside its container, this blog listens on port 8080. That port belongs to the container's own network namespace: its own loopback interface, its own virtual ethernet card and its own IP address on a private Docker bridge network. Your browser lives in a different namespace, the host's, and cannot see port 8080 in there until you ask Docker to connect the two.

Publishing a port

docker run --rm -p 9090:8080 blog-dotnet

Read -p 9090:8080 as host port : container port. Docker sets up forwarding so that traffic arriving at port 9090 on your machine is delivered to port 8080 inside the container. Open http://localhost:9090 and you are talking to the app.

A few variations come up all the time:

FlagWhat it does
-p 8080:8080Same port on both sides. The most common form.
-p 127.0.0.1:8080:8080Only reachable from your own machine, not from other devices on the network.
-p 8080Container port 8080 on a random free host port.
-PPublishes every port listed with EXPOSE on random host ports.

When Docker picks the host port for you, ask it which one it chose:

docker run -d --name blog-1 -P blog-dotnet
docker port blog-1
8080/tcp -> 0.0.0.0:55012
EXPOSE is documentation

EXPOSE 8080 in the Dockerfile does not open or publish anything by itself. It records which port the app expects to use, and -P reads it. Only -p or -P actually publishes.

Changing the port inside the container

This app reads a PORT environment variable, so the port on the inside can change too:

docker run --rm -e PORT=3000 -p 8080:3000 blog-dotnet

Now the app listens on 3000 inside the container, and you still browse to localhost:8080. The footer of each page prints the port the app is actually listening on, which makes the two sides of the mapping easy to see.

Stock ASP.NET Core images use a different variable, ASPNETCORE_HTTP_PORTS, which is set to 8080 in the base image. Our app reads PORT so that every sample in the training uses the same variable, and our Dockerfile clears ASPNETCORE_HTTP_PORTS so that the two settings never compete: 

ENV PORT=8080 \
    ASPNETCORE_HTTP_PORTS=

The bug everyone hits once: binding to localhost

Inside a container, localhost means the container's own loopback interface. Traffic forwarded by Docker arrives on the container's ethernet interface instead, so an app that listens only on 127.0.0.1 never sees it. The container is up, the port is published, and every request is refused.

The fix is to listen on 0.0.0.0, which means every interface. This blog does that explicitly: 

var port = int.TryParse(Environment.GetEnvironmentVariable("PORT"), out var p) ? p : 8080;
builder.WebHost.UseUrls($"http://0.0.0.0:{port}");

You are most likely to hit this with a launchSettings.json profile or an appsettings.json that pins http://localhost:5000. That works perfectly on your laptop and then silently breaks in a container.

Looking ahead to Kubernetes

Kubernetes has the same split, with different names. containerPort in a pod spec plays the role of EXPOSE, and a Service does the job of -p by giving a stable address that forwards to the pod's port. We build both in our first Deployment walkthrough.
